# Инструкция по Git для нашей команды: ОДИН репозиторий на всех

**Прочитай один раз полностью. Дальше пользуйся только Шпаргалкой из раздела 10.**

У нас нет отдельных репозиториев для фронта, бэка и презы. Есть один репо, например `hackathon-app`, и в нем лежит ВСЁ: код, база, доки и презентация. Это проще для хакатона, но требует дисциплины, чтобы не затоптать друг друга.

## 0. Как устроен наш один репозиторий

Примерно так:

```
hackathon-app/          <- ОДИН репо, клонируем один раз
├── index.php
├── assets/css/, assets/js/, assets/img/
├── includes/db.php     <- подключение к БД, трогает только тимлид
├── pages/
├── api/
├── database/schema.sql <- структура БД, трогает только backend + тимлид
├── docs/               <- чек-листы, деплой, идеи
└── pitch/              <- презентация! тоже здесь
    ├── presentation.pptx
    ├── presentation.pdf
    └── demo-video-link.txt
```

Вывод: вы все пушите в одно место, но в РАЗНЫЕ папки и РАЗНЫЕ ветки. Поэтому главное правило:

> **Своя задача = своя ветка = свои папки. Чужие папки без спроса не трогаем.**

Кто за что отвечает, чтобы не было конфликтов:
- Frontend: `pages/`, `assets/`
- Backend: `api/`, `database/`, `includes/db.php`
- Интегратор: все понемногу, но маленькими фиксами + мержи
- Green-1 (контент/тест): `assets/img/`, тексты внутри `pages/`, `docs/`
- Green-2 (преза): ТОЛЬКО `pitch/` + скрины. Никто больше в `pitch/` не лезет.
- Тимлид: `main`, `dev`, мержи, `schema.sql` контроль

## 1. Разовая настройка (15 минут, сделать ДО хакатона)

**Шаг 1. Установи Git и VS Code.**
Проверь:
```bash
git --version
```

**Шаг 2. Представься:**
```bash
git config --global user.name "Ivan Petrov"
git config --global user.email "ivan@example.com"
```
Почта = как на GitHub.

**Шаг 3. Склонируй НАШ ЕДИНСТВЕННЫЙ репо ОДИН РАЗ:**
```bash
git clone https://github.com/НАША-ОРГАНИЗАЦИЯ/hackathon-app.git
cd hackathon-app
```
Ссылку даст тимлид.

Все. Больше `clone` никогда не делаем. Дальше только `pull` и `push`.

В VS Code: `File -> Open Folder -> hackathon-app`.

Если просит логин/пароль: нужен не пароль, а Token. GitHub -> Settings -> Developer settings -> Personal access tokens. Попроси тимлида помочь заранее.

## 2. Ветки: всего 3 типа в одном репо

Так как репо один, ветки - это единственный способ не мешать друг другу.

- `main` - СВЯЩЕННАЯ. То, что на хостинге и на защите. Прямой пуш запрещен. Трогает только тимлид.
- `dev` - общая сборка. Все сливается сюда.
- `feature/номер-задачи-название` - твоя личная ветка. Живет 2-6 часов.

Пример:
```
main
 ↑
dev
 ↑  ↑  ↑
 |  |  feature/15-lead-form (backend)
 |  feature/12-header (frontend)
 feature/20-slides-update (преза)
```

Все трое работают параллельно в одном репо, но в разных ветках, поэтому не ломают друг друга.

Имена веток только латиницей:
- правильно: `feature/12-header`, `feature/15-login-form`, `fix/18-mobile-bug`, `pitch/21-slides-final`
- неправильно: `моя-ветка`, `финал`, `test`

Для презентации тоже отдельная ветка `pitch/...`, чтобы бинарный `.pptx` никого не блокировал.

## 3. Полный цикл работы от задачи до сдачи

Разберем на примере: тебе выдали Issue #12 "Сверстать шапку".

### Шаг 1. Обнови `dev`
Всегда начинаем с этого:
```bash
git checkout dev
git pull origin dev
```

### Шаг 2. Создай свою ветку ОТ dev
```bash
git checkout -b feature/12-header
```

Проверь где ты:
```bash
git branch --show-current
# должно показать feature/12-header
```

### Шаг 3. Работаешь в VS Code, сохраняешься часто
Правишь только свои файлы. Раз в 30-60 минут делай коммит:

```bash
git status
git add pages/header.php assets/css/style.css
git commit -m "12: добавил шапку и лого"
git push -u origin feature/12-header
```

Первый `push` с `-u`, дальше просто `git push`.

**Важно для одного репо:** не делай слепо `git add .`, если в `git status` видишь чужие файлы или `pitch/presentation.pptx`, который ты не менял. Добавляй точечно свои файлы, как в примере выше. Иначе затолкаешь чужое в свой коммит.

### Шаг 4. Создай Pull Request в `dev`
1. Зайди на github.com в наш репо.
2. Увидишь желтую плашку "Compare & pull request" - жми.
3. Проверь направление: `base: dev <- compare: feature/12-header`. **Должно быть в `dev`, НЕ в `main`!**
4. Название: `12: Шапка сайта`
5. В описание добавь `Closes #12`
6. Reviewers - выбери тимлида или мидла.
7. `Create pull request`.

Дальше ждешь. Если попросили доделать - правишь в ТОЙ ЖЕ ветке и снова `add/commit/push`. Новый PR создавать не надо, старый сам обновится.

### Шаг 5. После мержа - убери за собой
PR смержил проверяющий. Ты делаешь:
```bash
git checkout dev
git pull origin dev
git branch -d feature/12-header
```
Теперь ты на свежей `dev` и готов брать следующую задачу.

## 4. Правила коммитов в одном репо

Так как все в одном месте, по истории должно быть видно кто что сломал.

Формат: `номер-задачи: что сделал`

Хорошо:
```
12: сверстал шапку
12: поправил отступы шапки на мобилке
15: добавил сохранение заявки в БД
21: обновил слайды 1-5
```

Плохо:
```
фикс
правка
final
asdasd
```

Один коммит = одно логичное изменение. Не надо копить 5 часов и делать один гигантский коммит на 20 файлов - его невозможно проверить и откатить.

## 5. Как не потерять чужое: обновляйся 3 раза в день

Так как репо одно, `dev` уезжает вперед быстро.

Минимум утром, после обеда и вечером, находясь в СВОЕЙ ветке:
```bash
git pull origin dev
```

Если Git пишет `Already up to date` - отлично.
Если пишет про конфликт - иди в раздел 8, не паникуй.

Перед созданием PR обязательно сделай это же, чтобы проверить что твоя ветка дружит со свежей `dev`.

## 6. Презентация и картинки в том же репо: ОСОБЫЕ ПРАВИЛА

`.pptx` и `.jpg` - это бинарные файлы. Их нельзя нормально смержить как код. Если двое одновременно поменяют `presentation.pptx` - будет жесть.

Поэтому для папки `pitch/` железные правила:

1. **Презентацию правит ТОЛЬКО ОДИН человек** (Green-2). Остальные туда вообще не коммитят.
2. Он работает в ветке `pitch/...` и делает PR в `dev` как все.
3. Никаких `presentation-ФИНАЛ2-ИТОГ.pptx`. Только один файл: `pitch/presentation.pptx` + экспорт `pitch/presentation.pdf`. Перезаписываем их же.
4. Большие видео НЕ льем в гит. Видео заливаем на диск/YouTube (непубличная ссылка), а в репо кладем `pitch/demo-video-link.txt` со ссылкой.
5. Картинки для сайта кладем в `assets/img/` один раз с нормальными именами латиницей: `hero-team.jpg`, а не `IMG_20261007_12345.png`. Не дублируем одну картинку 3 раза.
6. Если тебе нужен скрин для презы - попроси Green-2, он сам положит в `pitch/`. Не лезь сам.

Тот же принцип для `database/schema.sql` - его меняет только backend + тимлид. Остальные не трогают.

## 7. Конфликты в одном репо (будут обязательно)

Конфликт = вы вдвоем правили одни и те же строки в одном файле. В одном репо это чаще всего `assets/css/style.css`.

Git покажет в файле такое:
```
<<<<<<< HEAD
.header { height: 60px; }
=======
.header { height: 80px; }
>>>>>>> dev
```

**Что делать зеленым (только так):**

1. Не закрывай VS Code, не жми случайные команды.
2. Открой файл с конфликтом. VS Code покажет кнопки: `Accept Current | Accept Incoming | Accept Both`. 
3. Напиши в чат: "У меня конфликт в style.css с @имя, чью оставляем?" Дождись ответа 2 минуты.
4. Выбери правильный вариант, убедись что строчки `<<<<`, `====`, `>>>>` пропали.
5. Сохрани, открой страницу в браузере - работает?
6. Заверши:
```bash
git add assets/css/style.css
git commit -m "12: помирил конфликт в style.css"
git push
```

Если страшно - сразу зови тимлида/мидла с фразой "конфликт в файле X, ветка Y". Это штатная ситуация, а не позор.

**Как уменьшить конфликты в одном репо:**
- В `style.css` договоритесь писать каждый в свой блок:
```css
/* === Ivan: header === */
/* === Maria: forms === */
```
- Не сиди в ветке больше 6 часов. Чем дольше сидишь, тем страшнее мерж.
- Перед правкой чужого файла спроси в чате: "Кто сейчас в login.php?"

## 8. ЗАПРЕЩЕНКА (за это ломается все)

🚫 `git push origin main` - прямой пуш в main. Запрещено всем кроме тимлида через PR.
🚫 `git push --force` - перезатирает чужую работу. Никогда.
🚫 `git reset --hard`, `git clean -fd` - стирают файлы. Только с тимлидом рядом.
🚫 Коммитить в один репо: пароли от хостинга, `config.local.php`, `.zip` архивы, папку `vendor/`, видео на 500МБ.
🚫 Создавать второй репозиторий "потому что так удобнее" или "я себе скопировал". Нет. Репо одно.
🚫 Править чужую папку из раздела 0 без предупреждения.
🚫 Мержить свой же PR самому без ревью (кроме мелкого фикса опечатки и то спроси).

Если тянет нарушить - напиши тимлиду, он подскажет как правильно за 1 минуту.

## 9. Кто что мержит

- В `dev`: может смержить тимлид или любой мидл после быстрой проверки (открывается? нет белого экрана?).
- В `main`: ТОЛЬКО тимлид. Схема: все готово в `dev` -> тимлид создает PR `dev -> main` -> проверяет -> мержит -> деплоит на хостинг.

Обычный разработчик кнопку `Merge` в `main` не жмет никогда.

```bash

git checkout dev
git pull origin dev
git checkout -b feature/12-название-латиницей

# ПОДТЯНУТЬ СВЕЖИЙ DEV К СЕБЕ

```

## 11. Для самых зеленых: как делать то же самое кнопками VS Code

1. Слева иконка Source Control (Ctrl+Shift+G).
2. Внизу слева видишь `dev` или свою ветку. Клик - смена ветки. Новая ветка: `... -> Branch -> Create Branch` от `dev`.
3. Поменял файлы - они появятся в списке. Наведи, жми `+` только на своих файлах.
4. Сверху поле Message - пиши `12: что сделал`, жми галочку (Commit).
5. Кнопка `Push` / `Sync` - отправить.
6. PR все равно создаем на сайте GitHub, не в VS Code.

Выучи 3 команды из консоли наизусть: `pull`, `checkout -b`, `push`. Остальное можно кнопками.

## 12. Частые косяки и лечение за 1 минуту

**1. `Please tell me who you are`**
Не сделал настройку. См. раздел 1 шаг 2.

**2. `rejected, failed to push`**
Сначала забери чужое, потом отдавай свое:
```bash
git pull origin dev
git push
```
Без `--force`.

**3. Начал менять файлы в `dev`, забыв создать ветку**
```bash
git stash
git checkout -b feature/12-название
git stash pop
```
Теперь изменения в новой ветке. Не коммить в `dev`.

**4. В `git status` видишь левый `pitch/presentation.pptx`, который не менял**
Не делай `git add .`. Добавь только свои файлы:
```bash
git add pages/about.php
```
А презу пусть пушит только ответственный.

**5. Создал PR в `main` вместо `dev`**
Срочно жми `Close`, создай новый в `dev`, напиши тимлиду.

**6. Напушил пароль от БД в репо**
Срочно скажи тимлиду. Он сменит пароль на хостинге после хакатона и потрет из истории. Сам не пытайся чистить историю.

**7. Потерялся: куча веток, не знаю где я**
```bash
git branch --show-current
git status
```
Скинь вывод тимлиду, он скажет 1 команду.

## 13. Тренировка за неделю до хакатона (обязательна всем)

Каждый должен пройти один раз:

1. `git checkout dev` + `pull`
2. Создать `feature/test-твое-имя`
3. Создать файл `docs/hello-твое-имя.txt` с текстом "Привет, я умею в PR в одном репо"
4. `add/commit/push`
5. Создать PR в `dev`, дождаться мержа
6. Удалить ветку, сделать `pull`

Не прошел без помощи - повтори еще раз. На хакатоне учиться будет некогда.

---
**Запомни формулу одного репо: 1 репозиторий = 1 `dev` + много маленьких веток + частые PR + не лезу в чужие папки. Коммить часто, пушь в свою ветку, спрашивай если страшно.**
